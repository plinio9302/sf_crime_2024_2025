SF Crime Analysis — 2024 vs 2025

An educational, self-contained walkthrough of a real Python + SQL analysis of 230,000+ San Francisco Police Department incident reports. Every panel below is annotated with what the underlying SQL query does and why — this dashboard doubles as a teaching artifact for the pipeline that built it.

Step 1 — The most important thing we found before trusting any number: the file SFcrime2025_processed.csv is not a clean calendar year. It's a rolling export that runs from 2025-01-02 through 2026-04-25, so 26,462 of its 121,194 rows are actually incidents dated in 2026. If you just count rows in "the 2025 file", crime looks like it went UP. Once you filter every query by the real IncidentDate year instead of which file a row came from, the conclusion flips to DOWN 13.78%. This is a classic "trust the data, not the filename" lesson — see Tab 5 for the exact SQL.

Step 2 — Which crime types and districts moved the needle? A window function (SUM(...) OVER (PARTITION BY incident_year)) computes each category's share of that year's total in one pass — no self-join needed. Then a separate JOIN compares raw counts year-over-year per category so we can rank the biggest movers.

Step 3 — Does crime follow a weekly or seasonal rhythm? Two GROUP BY queries on the cleaned view: one by day_of_week (derived with DAYNAME() in MySQL / the day-name column from the raw data here), one by incident_month. SQLite doesn't have MySQL's FIELD() function to force weekday order, so that sort is done in pandas instead — a good example of splitting work between SQL (aggregation) and Python (presentation logic).

Incidents by Day of Week

Wednesday and Friday are the busiest days; Sunday is the quietest.

Monthly Seasonality, 2024 vs 2025

Every single month of 2025 came in below its 2024 counterpart — a broad decline, not one outlier month.
Step 4 — Ranking districts by "safety." We define safety here purely as incident volume: RANK() OVER (ORDER BY COUNT(*) ASC) across the combined two-year total. Caveat: this measures volume, not severity or population density — a district could rank "less safe" simply because more people live or work there. Treat this as a starting point for further investigation, not a verdict.

District Safety Ranking (fewest incidents = safest)

Step 5 — The pipeline behind this dashboard, end to end:
  1. pandas.read_csv() loads the two raw SFPD CSVs (109,626 and 121,194 rows).
  2. df.to_sql() loads both DataFrames into a local SQLite database — no server required.
  3. A SQL view (sfcrime_combined_clean) unions the two years, drops rows with missing category/district, and derives incident_year straight from IncidentDate (never from which file a row came from).
  4. Nine SQL queries — the same structure as the original MySQL analysis — answer the case-study's questions: year-over-year totals, category/district/resolution breakdowns, day-of-week and monthly seasonality, and the district safety ranking.
  5. Each query's result is pulled back into pandas, exported to CSV for reuse, and bundled into dashboard_data.json — the exact numbers rendered in this dashboard.
  6. This HTML file embeds that JSON directly and renders it with Chart.js, so the dashboard opens and works completely offline — no server, no live database connection.
